# Part 1: Capabilities

## Capability catalogue

### Language and runtime

- TypeScript as ES modules, running in the browser.
- Compile target is ES2024 (`lib`: `ES2024`, `DOM`, `DOM.Iterable`). `tsc` only type-checks (`noEmit`), Vite builds the bundle.
- `tsconfig.json` extends `@combeenation/ts-config`.

### Custom code entry point

- Runs project code once the configurator is ready: controls are created and rendered and the product plan is loaded.
- The entry file is `src/index.ts`. The build output must be a single ES module named `cfgr.js` with no extra chunks. Top-level await is supported.
- Use it for initialisation and registering behaviour. Functions can be exposed on the global `window.CbnCustomCode` object, for example for debugging in the browser console.

### Custom control rendering (`CustomControl`)

- Gives custom code a DOM element inside the configurator to render into, independent of any UI framework: `control.render(element => { /* mount UI into element */ })`.
- The control must exist in the configurator and be declared in the generated typings. Import it from there.

### Value components (`ValueComponent`)

- Exchange values between custom code and configurator components. The component must exist in the configurator and be declared in the generated typings, with a value type per component.
- `component.onValueChanged(listener, callImmediately?, condition?)` subscribes. With `callImmediately: true` the listener is called at once with the current value, otherwise only on changes. `condition` is a predicate that decides whether the listener is called.
- `component.setInput(value)` writes. `component.name` reads the identifier.
- `onValueChanged` returns a promise whose result exposes `unsubscribe`. Unsubscribing will be supported once the SDK package is released. Until then it depends on the SDK build. Subscribe on mount and unsubscribe on cleanup where supported.

### Generated configurator typings

- Typed handles (`ValueComponent`, `Panel`, `CustomControl`) named after the configurator's elements, plus data types and Zod schemas. Import them from `src/typings/cfgr-defs.generated.ts` instead of constructing them by hand.
- The file is generated by the connected dev server instance on the platform, via the sync plugin (see Build and sync tooling). Never edit it by hand and exclude it from linting.
- It imports `zod`, which the SDK installs as a dependency.

### 3D viewer

- Renders a 3D scene on a canvas, using `@combeenation/3d-viewer` (which re-exports Babylon.js types). Needs a `<canvas>` element.
- `new Viewer(canvas, options)`, with meshes and materials built via `MeshBuilder` and `PBRMaterial`.
- `viewer.cameraManager.autofocusActiveCamera()` focuses the camera. `viewer.engine.resize()` when the canvas size changes.
- Call `viewer.destroy()` when the viewer is no longer needed, to release resources.

### Build and sync tooling

- Vite with `@combeenation/vite-plugin-custom-code-sync` (`CbnCustomCodeSync`). The plugin is required for the connection to the platform, which provides the generated typings.
- The output is one ES module, `cfgr.js`, with dynamic imports inlined (`inlineDynamicImports: true`). CSS must be injected into the JS bundle, because there is a single output file (the reference project uses `vite-plugin-css-injected-by-js`).
- Needs `cbn.config.json` and a Vite config that sets the entry to `src/index.ts`.

### Configurator link (`cbn.config.json`)

- Links the project to a Combeenation company and configurator, declared in `cfgrLinks.companies[].cfgrs[]`. The concrete company and configurator are read from the project's own file.
- The file sits in the project root. The generated typings and the sync plugin depend on it.

### Standard npm scripts

- `npm run dev`: Vite dev server plus `tsc --watch`.
- `npm run build` / `npm run build:dev`: run `check-code`, then `vite build` (the latter with `--mode development`). Builds fail when lint or type checking fails.
- `npm run check-code`: `eslint` and `tsc`. Run it before finishing a change.
- `npm run format`: Prettier.
- Project scripts are defined in the project's `package.json`.

## Cross-cutting guidance

- **Environments and deployment:** The built `cfgr.js` is uploaded on the platform. Other target environments are not documented.
- **Identity and access:** Not documented. The generated typings can include user and tenant data types, depending on the configurator.
- **Observability and operations:** Not documented.
- **Security and data handling:** Not documented.

# Part 2: Approved libraries

This part describes the organization's guidance for platform libraries. A library being present in an existing project does not automatically mean every version or use case is approved.

## Library catalogue

All published npm versions of the libraries below are supported, and the latest version is always recommended. Never use a local build (for example a tarball) in production. Other support details have not been confirmed.

### @combeenation/custom-code-sdk

- Connects custom code to the configurator (`ValueComponent`, `CustomControl`, `Panel`). See Part 1 for subscriptions, writes and custom control rendering.
- Needs the generated typings in `src/typings/cfgr-defs.generated.ts`.
- It depends on `zod`, which the generated typings import directly. Do not declare `zod` as a peer dependency for now.
- Unsubscribing from value changes is supported once the package is released.

### @combeenation/3d-viewer

- 3D rendering. It re-exports Babylon.js types such as `Color3`, `MeshBuilder` and `PBRMaterial`. See Part 1 for rendering a scene on a canvas.
- Needs a canvas element.

### Build and quality tooling

- `@combeenation/vite-plugin-custom-code-sync`, `@combeenation/ts-config`, `@combeenation/eslint-config` and `@combeenation/prettier-config`.
- `tsconfig.json` extends the shared TypeScript config, `eslint.config.mjs` extends the shared ESLint config and `vite.config.js` registers the Vite plugin.

## Dependency selection rules

1. Prefer libraries already approved for the required use case.
2. Use the latest published version unless the project has a documented reason to pin another one.
3. Never use local builds (for example a tarball of the SDK or the viewer) in production.
4. Verify maintenance, compatibility, security, licensing, and platform requirements according to organizational policy.
5. Explain the reason and trade-offs before proposing a new dependency.
6. Do not claim that a library is approved solely because it is already installed.
7. When sources conflict, flag the conflict and seek confirmation from the library or platform owner.
